# Changelog

## 0.14.1 

Stage 2 of the 0.13.3 code review: packaging, hardening, CI. No
configuration change is needed. New, all optional: `daemon.command_user` and
a `user` on `exec` actions, notification commands and command health checks;
`notify.details` (`safe` by default — see below).

### Fixed
- **The package did not install, and its binaries did not start, on Debian
  12 or Ubuntu 22.04.** 0.14.0 declared `libc6 (>= 2.39)`. The review
  assumed lowering it would do, because std references `pidfd_spawnp` and
  `pidfd_getpid` (glibc 2.39) only weakly — but the binary's version-needs
  entry for `GLIBC_2.39` is not marked weak (neither lld nor GNU ld does
  that), so the loader refuses it anyway: "version `GLIBC_2.39' not found".
  Release packages are now linked on the oldest supported base, Ubuntu 22.04
  (`scripts/build-deb.sh --portable`, the CI package job): they need glibc
  2.34, `Depends: libc6 (>= 2.34)` is what `dpkg-shlibdeps` reads from them,
  and `scripts/check-glibc.sh` fails a release that needs more. Checked by
  installing and starting the package in clean Debian 12 (glibc 2.36),
  Ubuntu 22.04 (2.35) and 24.04 (2.39) systems.
- **A hook's timeout killed only the hook** (B23): what it had started
  (`curl` under a shell script) went on running with the daemon's
  privileges and held its pipes. Every program Warden runs is now the
  leader of its own process group, and a timeout kills the group.
- **Secrets in notifications.** Event details carry text Warden did not
  write — integrity diffs of `/etc/environment` or a unit's `Environment=`,
  the journal tail of a failed unit, command lines like `mysql -pSECRET` —
  and the first eight details went to Telegram/Slack, the whole event to a
  JSON webhook. With `notify.details = "safe"` (the default) secrets are
  masked before anything is rendered for a webhook, Telegram or a
  notification command: command-line passwords, `KEY=value` and `"key":
  "value"` credentials, `Authorization`/`Cookie` headers, `Bearer`/`Basic`
  tokens, URL credentials, PEM private keys, crypt hashes and well-known
  token formats become `***`. `none` sends only kind, severity, title,
  subject and actions; `all` sends everything. The journal and `exec`
  hooks keep the original.
- **A flood could push a finding out of the event queue.** The queue
  from the detectors to the engine (8192 events) dropped whatever came
  when it was full; noise generated by an attacker could hide a real
  finding. It now gives up the oldest event of the lowest priority below
  the newcomer's (severity, one level up for `security.*`; resolutions and
  `action.*` results rank high), and events still leave in arrival order.
  `warden_events_dropped_total` has a `priority` label.
- **A kill waited behind a cleanup.** The executor ran everything in one
  queue: a 5-minute `apt-get clean`, a 2-minute journal vacuum, a
  `systemctl restart` or a hook delayed the kill of a process exhausting
  memory. Containment (`kill`, `stop`, `freeze_cgroup`, `kill_cgroup`,
  `block_ip`, `quarantine`, `throttle`) now has a lane of its own; the
  lanes share one set of circuit breakers (budgets, cooldowns, snapshot
  interval), and every kill is in the urgent lane, so two kills never race.
- **Found by the new fuzz targets:** a D-Bus signature `a()` (an array of
  empty structs, forbidden by the specification) made the unmarshaller
  loop, appending values without reading input — 23 bytes exhausted
  memory; an access-log time with out-of-range fields overflowed the
  timestamp arithmetic; a mountinfo escape `\545` overflowed a byte. Each
  is fixed and kept as a regression seed.
- `wardenctl events | head` (any `wardenctl` output cut short by its
  reader) ended with a panic, "failed printing to stdout: Broken pipe";
  it now ends quietly, like other Unix tools.
- `scripts/check-seccomp.sh` passed vacuously since 0.14.0: its test
  configuration was refused by the stricter validation, the daemon exited at
  once and the trace was empty. The configuration is fixed, and the script
  fails when the daemon does not start or exits during the trace.

### Security
- **Hooks without root.** `exec` actions, notification commands and command
  health checks ran as root with all of the daemon's capabilities
  (`CAP_SYS_ADMIN`, `CAP_DAC_OVERRIDE`…). `daemon.command_user` (or `user`
  per item) runs them as another account: groups, gid and uid are switched
  in the child before `exec`, which drops every capability; an unknown user
  fails the hook instead of falling back to root, and `--check-config`
  warns about it. The unit gains `CAP_SETUID`/`CAP_SETGID` for the switch;
  the package and `install.sh` create the system user `_warden` for it. The
  default is unchanged (root). What these programs run is not taken for a
  web worker's children, even when the account is one of `web_users`
  (`nobody`) — that would have alerted on itself in a loop.
- **Unit:** `@mount` is no longer in `SystemCallFilter` (it was there for
  "statfs-family helpers", but `statfs` is in `@file-system`; with
  `CAP_SYS_ADMIN` it allowed `mount`, `pivot_root`, `move_mount`);
  `RestrictAddressFamilies=AF_UNIX AF_INET AF_INET6 AF_NETLINK`,
  `ProtectKernelModules=yes`, `ProtectHostname=yes`. `check-seccomp.sh`
  also verifies the socket families against a trace. `systemctl reload`
  validates the configuration first and fails with the reason, instead of
  reporting success while the daemon keeps the old configuration.
  `wardenctl doctor` flags an installed unit that still allows `@mount`,
  blocks a needed address family or lacks `CAP_SETUID`/`CAP_SETGID`.

### Packaging
- `dpkg --purge` keeps `/etc/warden/conf.d` and `signatures.d` when they
  hold the operator's files (it used to delete them).
- `scripts/test-deb-install.sh`: install, every profile validates, start,
  `/health`, control socket, clean stop, purge.

### CI
- `coverage`: `cargo llvm-cov` on every push and pull request; the number
  is in the job summary and a comment on the pull request; the build fails
  below `.github/coverage-floor` (77 %; now 79.3 % of lines) or when it falls
  more than half a point below main's last measurement.
- `fuzz`: cargo-fuzz targets for every parser of untrusted input — access
  logs, the three ModSecurity formats, D-Bus messages and bodies, the proc
  connector, fanotify FID records, `/proc` and `/sys` text, `auth.log`, the
  secret redactor — one minute each. The bodies live in `crates/warden-fuzz`,
  where `cargo test` runs them on stable over a seed corpus and
  deterministic mutations.
- `package` builds the `.deb` on Ubuntu 22.04; `install` installs and starts
  it in Debian 12, Ubuntu 22.04 and 24.04 containers.

## 0.14.0 

Stage 1 of the 0.13.3 code review: the lifecycle of what Warden reports,
reloads that keep what was learned, and trust in input it does not control.
No configuration change is needed; `systemd.max_restarts_per_hour` is now
the only restart budget (see below), and the validation catches more
mistakes — a configuration that 0.13.4 accepted may be refused if it has an
invalid glob, a zero interval or a cleanup target above where the cleanup
starts.

### Fixed
- **A reload rebuilt every detector** (B6). Open incidents were never
  resolved (the new tracker started at "ok"), a condition that still held
  was raised anew (for memory: a second kill before `repeat`), the process
  scan was a "first scan" again (everything `found_at_startup`), a critical
  disk started a new `du` walk on every reload, and the SUID walk was
  rescheduled. Detectors now declare the configuration sections they are
  built from: unchanged ones are kept as they are, changed ones adopt the
  new configuration and keep their levels, open conditions, baselines and
  schedules (`Detector::reconfigure`); only a detector that cannot is
  replaced — and a disabled one removed — after its open conditions are
  resolved (`closed_by: reload`). Its level and tick metrics go with it.
- **Conditions without an end** (B10). `process.cpu_hog`,
  `process.limit_exceeded`, `process.uninterruptible`, `limits.process_fds`,
  `security.miner`, `security.miner_port`, `security.reverse_shell` and
  `process.zombies` repeated every 10 minutes (hourly for zombies) for as
  long as they held, and were never resolved; `disk.inodes` never stepped
  down nor resolved; `network.*` counters never resolved; `disk.readonly`
  said nothing about a filesystem already read-only at startup and nothing
  when it became writable. All of them now follow one lifecycle
  (`warden_core::condition`): reported when they start, reminded with an
  exponential back-off (10 min, 20 min, … at most daily), resolved when they
  stop.
- **"Resolved" for what was never notified** (B9): with `min_severity =
  "critical"` the chat got "cpu.pressure resolved" for warnings it never
  saw. A resolution is sent only where its condition was — globally and per
  channel (webhook, Telegram, command with their own `min_severity`).
- **Budgets charged for actions that did not run** (B11, B12). A kill of a
  protected process or of one already gone, a dry run, used up
  `max_actions_per_hour` / `max_kills_per_hour`; the systemd detector
  charged its own restart budget before knowing whether anything would be
  restarted — in dry-run three failures "exhausted" it, and the first real
  restart after `dry-run off` was refused — while the responder kept a
  hard-coded 4/hour of its own. Budgets are now consulted first and charged
  for attempted actions only; `systemd.max_restarts_per_hour` is the one
  per-unit restart budget, the detector only counts failures (critical when
  a unit fails more often than its budget within an hour).
- **`kill { tree = true }` was slow and racy** (B13): descendants were
  terminated one by one, up to 500 ms each, while the parent kept forking;
  a large tree held the responder for minutes. The tree is now stopped
  first (the parent, then whatever it forked meanwhile, until nothing new
  appears), then killed, under one deadline (`grace`, at least a second);
  when the tree is everything in its unit's cgroup, `cgroup.kill` does it
  atomically. (A tree kill is a hard kill: there is no SIGTERM phase.)
- **Paging activity never ranked the first victim** (B14): the major-fault
  rate was measured between two rankings, and the first one — the kill
  decision — had no history. It is sampled from the first elevated reading
  on; `wardenctl top` measures it over half a second (it always showed 0).
- **The access log trusted the client** (B15): the time was taken from the
  first `[` of the line, and the user field before it comes from the
  client's `Authorization` header — one request with `[01/Jan/2099…]` as its
  user pushed every other request out of the correlation ring. The time is
  now the last bracketed field before the request; the ring is bounded by
  when lines arrived; a non-ASCII time zone no longer panics the sensor.
- **Realtime FIM correlated around the file's mtime** (B16), which a
  dropper sets to an old date: the requests around the write itself are
  used now (the scheduled scan, which has nothing better, keeps the mtime).
- **Trust by path** (B17): `is_system_binary` checked the path string in
  Warden's own view — a process in a container started as `/usr/bin/git`
  passed for the host's git (`fim.trusted_writers` accepted its writes to a
  bind-mounted site), and a root-owned `sshd` inside a container got the
  protection of the host's. Trust now requires Warden's mount namespace and
  the inode behind `/proc/<pid>/exe` to be the one at the path.
- **Watchdog on the wall clock** (B18): an NTP step or a resume from suspend
  withheld `WATCHDOG=1` and made `/health` answer 503. The heartbeat runs on
  the monotonic clock.
- **Journal write errors were silent** (B19). A full disk could leave a
  half-written line (invalid JSON) and a failed rotation was retried on
  every event. The journal has a writer thread of its own (a hung disk no
  longer holds the engine, `status` and `/health`), cuts a failed write back
  to the last complete line, repairs a partial last line on open, counts
  failures (`warden_journal_write_errors_total`, `warden_journal_dropped_total`)
  and backs off a failed rotation.
- **State and metrics that grew for ever** (B20): `warden_disk_full_eta_seconds`
  kept its last value on a disk that stopped growing; counters, trackers and
  `warden_iface_errors_per_second{iface}` series of vanished interfaces
  (containers, VMs, VPNs) were kept in locked memory; the tick series of a
  disabled detector stayed after a reload.
- **Validation gaps** (B21): a zero `interval` of any detector made its
  scheduler spin; invalid globs in `cpu.hog_ignore`,
  `memory.culprit.prefer/avoid`, `systemd.ignore/auto_restart`,
  `network.ignore_interfaces`, `process.ptrace_allow/miner_names/db_comms`,
  `process.allowed_children`, `integrity.suid_exclude`,
  `fim.site.signature_exclude` were dropped silently; a
  `cleanup_target_percent` at or above where the cleanup starts skipped
  every step. All are configuration errors now.

### Changed
- `wardenctl status` shows the level of every detector that has one
  (memory also while calm; network, hardware and process findings are new).
- `warden.reloaded` is a `notice` with `restart_required` when a changed
  setting is read only at startup (`daemon.state_dir`, `runtime_dir`,
  `control_socket`, `log_level`, `log_format`, `mlock`, `oom_score_adj`,
  `malloc_arenas`, `hostname`, `metrics.*`).
- Fingerprints follow one convention, checked by a test on the sources: the
  first segment is the kind, severities are lowercase
  (`limits.pids:warning`, not `:Warning`), `:resolved` exactly on
  resolutions. Renamed: `hardware.ue/ce:*` → `hardware.memory_uncorrected/
  memory_corrected:*`, `system.clock` → `system.clock_unsynchronized:*`,
  `kernel.module:*` → `security.kernel_module_loaded:*`, `lsm:*` →
  `security.lsm_disabled:*` / `security.lsm_profiles_unloaded:*`,
  `heuristics.ip:*` → `heuristics.ip_threshold:*`; conditions carry the
  severity (`network.listen_overflow:warning`, `disk.readonly:/data:critical`,
  `process.cpu_hog:<pid>:<start>:warning`). Policies match on `kind`, not
  fingerprints, and are unaffected.
- The cooldown of point-in-time process findings runs on the real clock.

## 0.13.4 

Stage 0 of the 0.13.3 code review ("stop valves"): the defects that can make
a remediation do harm — act on the wrong file, keep acting when it does not
help, act when the operator said not to, or leave the host unprotected after
an upgrade. Two configuration additions with safe defaults
(`memory.max_kills_per_episode`, `age_from`/`exclude` of `delete_old`); the
shipped `/tmp` step uses them. Drop-ins that set a playbook now replace it
(see below).

### Security
- **Symlink races in cleanup and quarantine** (B1, B7). `delete_old` and
  `truncate_large` checked a path with `lstat` and then acted on the path:
  a user who owns a directory under `/tmp` (or a web worker in a site) could
  swap it, or the file, for a symlink in between and have root delete or
  truncate files elsewhere; quarantine renamed the name it had examined and
  then `chmod 000`-ed the blob *by path*, following a symlink swapped in
  meanwhile. Reproduced in tests: 37 of 100 victim files deleted, a victim
  truncated, a victim `chmod 000` in 30 ms. A new module,
  `warden_sys::safefs`, does everything on directory descriptors —
  `O_NOFOLLOW` opens component by component, `fstatat`, `unlinkat`,
  `openat`, `renameat2(RENAME_NOREPLACE)` relative to the directory, and a
  check that the name still refers to the inode that was examined — and
  decides policy on the path the descriptor really has. `delete_old`,
  `truncate_large`, `truncate_deleted`, quarantine `put`/`restore`, the
  `largest_files` evidence of `disk.space` and the `du` walk of
  `disk.usage_report` use it. On the way to a configured root a symlink is
  followed only if root or the owner of its directory owns it (the
  `fs.protected_symlinks` rule). `truncate_large` refuses a file with other
  hard links; `restore` never replaces an existing file, follows only root's
  own symlinks on the way back (a site user's `uploads -> /etc` is refused,
  an operator's `/var/www -> /srv/www` works) and sets the owner before the
  mode (`chown` cleared set-id bits). Race tests flip directories and files while the
  action runs; they fail on 0.13.3.

### Fixed
- **`wardenctl dry-run off` was undone by the next reload** (B2). The
  runtime switch lived in memory: a `SIGHUP` (logrotate, a deploy hook) or a
  restart silently put the configuration's value back. The override is now
  stored in `/var/lib/warden/dry-run.json` and kept across reloads and
  restarts, until `wardenctl dry-run reset` or a change of `dry_run` in the
  configuration (a deliberate edit wins over an older override). Every change
  of the effective mode — from the socket, a reload, a dropped override — is a
  `warden.dry_run` event with its `source` and `reason`; `wardenctl status`
  shows what decided the mode. `--dry-run` cannot be switched off from the
  socket.
- **Drop-ins appended to playbooks** (B3). Any array whose new value
  consisted of tables was appended, so `web_spawn = [{ do = "kill", … }]` or a
  `disk.cleanup` written as tables in `conf.d/` was added to the main file's
  list instead of replacing it. Only record collections are appended now
  (`fim.site`, `policy`, `notify.webhook`, `notify.command`,
  `process.limit`, `process.allowed_children`, `waf.log`, `health.check`,
  `kernel.patterns`); everything else is replaced.
- **Memory kills went on when they did not help** (B4). With the pressure
  held by a tmpfs file, shared memory or kernel slab, every `repeat` killed
  the next service. The culprit ranking now counts what a kill frees —
  `RssAnon + VmSwap` (`RssShmem` and file pages are not freed; the RSS on
  kernels before 4.5) — and every kill is checked once its victim is gone: if
  MemAvailable did not rise by at least half of what the victim held, kills
  stop for the rest of the episode (`memory.kill_ineffective`, with Shmem and
  unreclaimable slab and where to look). Kills that do help are capped by
  `memory.max_kills_per_episode` (default 3); the same applies to swap
  storms. A kill that did not happen (dry-run, refused, cooldown) is not
  judged. `wardenctl top` shows the anonymous memory.
- **`act_on_existing = false` was bypassed by the heuristics** (B5). The
  startup scan stripped the actions of processes that predate Warden, but the
  same events raised their suspicion score to `heuristics.contain`, whose
  `on_contain` acted anyway; a policy `alert_only` had the same hole. Such
  events carry `actions_withheld`: they count towards the score but can not
  make the heuristics contain a process (`heuristics.suspicious` says
  `containment_withheld`) — like `ip_block_off` for addresses.
- **A CMS update killed the PHP worker** (B8). A FIM mass change killed every
  web writer in the window: an update from the CMS admin changes hundreds of
  files through the same worker. Only writers whose own writes in the window
  matched the signatures are killed now, and only such a burst is an
  `emergency`; a burst of clean changes is a `warning` with a hint to pause
  FIM around updates (`wardenctl fim pause <site> 30m`, see
  [integrations.md](docs/integrations.md)). Malicious writes count towards
  the burst.
- **The `/tmp` cleanup step ignored `systemd-tmpfiles` rules.** It aged files
  by mtime (a file still read every day, or extracted with an old mtime, was
  deleted after 10 days) and entered `systemd-private-*` directories of
  running services and X server sockets. `delete_old` gets `age_from =
  "newest"` (the newest of atime, mtime and ctime — `touch -d` cannot make a
  file look old) and `exclude` globs (a matching directory is not entered);
  the default `/tmp` step uses both. Cleanup globs are validated.
- **An upgrade with an invalid configuration stopped the daemon.** The
  package restarted the service unconditionally; the unit's `ExecStartPre`
  check then failed and the host was left unprotected (the postinst even
  printed "the service was not started"). The postinst now restarts on
  upgrade only if the configuration validates with the new binary;
  otherwise the old daemon keeps running and the problem is printed.

### Changed
- `delete_old` and `truncate_large` walk at most 2 000 000 entries / 120 s
  per step and say when the budget cut them; a step stops at `max_files`
  as it goes instead of collecting four times as many candidates first.
- `quarantine_allowed`/`cleanup_allowed`/`resolve_parent` are gone
  (`check_quarantine_path`/`check_cleanup_path` are pure checks of a real
  path); `fsflags` works on descriptors.

## 0.13.3 

Sprint 2 of the 0.13.0 review
(§3.1):
time that a person configures and reads is real time, sleep included. No
configuration change is needed.

### Fixed
- **Intervals shrank by the time the machine was suspended** (§3.1).
  `Instant` is `CLOCK_MONOTONIC`, which stops during suspend: on a laptop or
  a desktop that sleeps at night, "once a day" became "once per 24 h awake",
  a 15-minute dedup window or a per-hour budget stretched over the night,
  and ages shown in events (`biggest_dirs_age`, "next attempt in") were short
  by the sleep — 2 h 20 min in the review log. A new clock,
  `warden_sys::clock::now()`, adds the time slept since the daemon started
  (`CLOCK_BOOTTIME` − `CLOCK_MONOTONIC`) to the monotonic clock and is now
  used for:
  - the engine's and the notifier's dedup windows and the notification
    budget;
  - per-target action cooldowns, `max_actions_per_hour`,
    `max_kills_per_hour`, per-unit restart budgets, `snapshot_min_interval`;
  - suspicion decay (`heuristics.half_life`);
  - disk reminders and cleanup back-offs, `usage_report_every`, the
    prediction alert's hourly limit, `biggest_dirs_age`;
  - the SUID walk schedule (`suid_interval`) and FIM's scheduled scans,
    `wardenctl fim pause`, and its one-hour memory of blocked addresses.

  Sustain and hysteresis (`sustain`, `clear_after`) stay on the monotonic
  clock on purpose: two readings eight hours apart around a suspend are not
  pressure held for a minute. A scan that fell due during the night runs
  after resume — paced and, if the disk is busy, postponed (0.13.1).

### Tests
- `warden-sys` has a `test-util` feature (`clock::simulate_suspend`, never in
  a release build); `tests/suspend.rs` in `warden-respond` and
  `warden-detect` show a cooldown and an hourly budget running on, and a
  daily SUID walk falling due, while the machine "sleeps".
- The `/sys` readers for EDAC and thermal zones are tested on fake trees
  (they had no coverage: CI machines have neither).

## 0.13.2 

Sprint 1 of the 0.13.0 review
():
the last two findings with regression tests are fixed, the fast-scheduler
detectors get tests on synthetic series, and those tests and the e2e run
turned up two more defects, fixed here too. No configuration change is
needed.

### Fixed
- **"recovered" for a failed unit that was only being started again**
  (§3.3). A timer-started oneshot (`fwupd-refresh.service`) that is
  `activating` during a reconciliation is not in the failed list, and was
  reported as recovered — then failed again at the next run. Reconciliation
  now also asks systemd for `activating` and `deactivating` units (one
  `ListUnitsFiltered` call over D-Bus; `systemctl list-units
  --state=failed,activating,deactivating` when polling), and a failed unit
  that is starting or stopping stays failed until it settles: a signal or
  the next reconciliation tells how it ended.
- **Heuristics blocked addresses the operator said not to block** (§2.6).
  With `auth.ssh_block = false` an SSH brute force (60 points) reached
  `heuristics.ip_block_score` (60) on its own and the heuristics added the
  block. Events whose source deliberately does not block now carry
  `ip_block_off` with the reason: `auth.ssh_block = false`,
  `waf.block = false`, `fim.block_attackers = false`, or a `[[policy]]` that
  made the event `alert_only` or took its `block_ip` away; an allowlisted
  address counts the same. Such an event still adds to the address's score,
  but it does not trigger the heuristics' block — a later finding from a
  source that does block may. To never block at all:
  `[actions.firewall] enabled = false`; `block_ip` is then *refused*, not
  *failed*.
- **"warning → resolved → warning" was lost by CPU, I/O, memory, limits and
  disk alerts.** Their condition fingerprints carry the severity or the PID
  (`cpu.pressure:warning`, `disk.space:/:critical`,
  `memory.pressure:warning:1234`) while the resolution is `…:resolved`, so
  the counterpart rule of 0.13.1 (`X` ↔ `X:resolved`) did not connect them:
  pressure that came back within the notifier's 15 minutes was taken for a
  repeat, and the chat kept showing "resolved". The rule now is: `X:resolved`
  ends `X` and every `X:…`; a condition ends the resolutions of every
  colon-prefix of its fingerprint (`warden_core::event::end_episodes`, used by
  the engine and the notifier).
- **A `disk.space` alert — and its cleanup — waited for a walk of `/tmp`.**
  The "largest files" evidence is gathered before the event is emitted; its
  entry budget only ended the directory being read, and every directory
  already queued was still listed. With 200 000 directories under `/tmp`, a
  cold cache and writeback going on, that took 2.6 s for `/tmp` alone, and
  the e2e test's "cleanup within 10 s" failed four times in a row right
  after a coverage run (not reproduced since; the walk is the slow step
  found). Both budgets now stop the whole walk, and the evidence has a 1 s
  deadline (measured ≤ 1.2 s under the same load); the event then carries
  `largest_files_partial: true` — `wardenctl du` has the full picture.

### Tests
- The review's §3.3 and §2.6 tests run by default: all six regression tests
  of the 0.13.0 review now pass.
- Detectors of the fast scheduler — CPU, I/O, memory, limits, network,
  hardware — are split into reading and deciding (`CpuSample`,
  `MemorySample`, `LimitsSample`, `HwSample`, …), and the deciding part is fed
  synthetic series: sustain and clear times, warning → critical, repeats
  while critical, episode length, swap storm, OOM deltas, fork storms,
  auto-grow of a limit, the binding PID limit, counter rates, ECC deltas,
  thermal and clock (audit §6, open since the 0.12 audit).
- New tests for unit snapshots (D-Bus fake filters by state now), policies
  that take a block away, `end_episodes`, and the whole-walk budgets.
- The e2e shutdown check allows for an instrumented build writing its profile
  on exit (only when `LLVM_PROFILE_FILE` is set).

## 0.13.1 

Sprint 0 of the 0.13.0 review
():
four small fixes with regression tests, plus pacing of background scans by
I/O pressure. No configuration change is needed; the new `[daemon.pacing]`
section is on by default.

### Fixed
- **A link that came back up never closed its "link down" incident**
  (§3.4). `network.link_down` and `network.link_up` now follow the
  convention of every other condition: the resolution's fingerprint is the
  condition's plus `:resolved` (`network.link:enp4s0` →
  `network.link:enp4s0:resolved`). The review suggested one shared
  fingerprint; that would have made the engine drop the Info "up" that
  follows a Warning "down" within the dedup window, so the convention was
  kept instead. Link events are state changes: each change is reported once
  per interface, and a flap (down, up, down within a minute) is no longer
  swallowed by the analyzer's cooldown.
- **De-duplication now knows that a condition and its resolution
  alternate**: in the engine (`events.dedup_window`) and in the notifier
  (`notify.dedup_window`), a resolution ends the condition's episode and the
  next occurrence is new, not a repeat. Before, "down, up, down" within the
  window lost the second "down", and the chat kept showing "up".
- **A dry run started the cooldown of the real action** (§2.3): after
  `wardenctl dry-run off` the first real occurrence was skipped as "ran
  recently"; an action refused by the hourly budget blocked the next attempt
  the same way. The per-target cooldown is now armed only when the action has
  really run (done or failed).
- **"metadata changed" for a file rewritten with the same bytes** (§5.2):
  `integrity` no longer reports a file whose content, mode and owner did not
  change (a cron job rewriting an apt source via "temp + rename"); the
  baseline is refreshed quietly. A `chmod` or `chown` is still reported, and
  is now noticed even within the same second as the previous check (mode and
  owner are part of the cheap change check).
- **`fs.suid_dumpable = 2` was flagged on hosts that pipe core dumps**
  (§5.3): with `kernel.core_pattern` starting with `|` (apport,
  systemd-coredump) it is the intended setting and is no longer advised
  against.
- `scripts/check-seccomp.sh` runs the daemon with `dry_run = false` again,
  so the helpers of the actions are traced (since 0.13.0's observe-only
  default they were not).

### Added
- **Background scans yield to the workload** (`[daemon.pacing]`, see
  [docs/performance.md](docs/performance.md#background-scans-and-io-pressure)).
  The disk-usage walk, the SUID/SGID walk and scheduled FIM scans measure the
  I/O pressure other tasks feel (PSI `some`, measured while the scan pauses,
  so the scan's own waits do not count) and work in 200 ms quanta with
  pauses: above `io_pressure` (10 %) the duty halves, down to a floor (¼ for
  the disk walk, ⅒ for the SUID walk, ½ for FIM, whose worker handles
  real-time writes only between scans), and grows back on a quiet disk. The
  scanning thread is in the idle I/O class while the disk is busy and in
  best-effort 7 while it is quiet (`io_class = "adaptive"`), so that a quiet
  host's occasional write does not stall it. A scheduled SUID or FIM rescan
  that finds the disk busy is postponed by 2 min, for at most `max_defer`
  (1 h); the first baseline and a walk after lost real-time SUID events are
  not. The disk walk's `usage_report_max_time` counts working time; its wall
  time is capped at 4×. Operator-started scans (`wardenctl du`,
  `wardenctl fim scan`) and cleanup actions are never paced.
- `wardenctl status` shows a `Pacing:` line; `/metrics` exports
  `warden_pacing_duty`, `warden_pacing_active`,
  `warden_pacing_paced_seconds_total`, `warden_pacing_deferrals_total` and
  `warden_pacing_io_pressure_ratio` per scan; `disk.usage_report` carries
  `paced_seconds` when the walk yielded; FIM scan results carry
  `paced_seconds` and `wardenctl fim status` `scan_postponed_for_seconds`.
- `wardenctl doctor` shows the I/O scheduler of `/` and of the FIM sites:
  `none` and `kyber` (the NVMe default) ignore I/O classes, and there only
  pacing keeps scans out of the workload's way.

### Tests
- The review's regression tests for §2.3, §3.4, §5.2 and §5.3 run by
  default now; §2.6 and §3.3 stay ignored until Sprint 1. New tests for the
  dedup counterpart rule (engine and notifier), `Cooldown::cooling`/`arm`,
  the `suid_dumpable`/`core_pattern` matrix, the pacing controller (with a
  fake PSI whose own-stall accrues only while the scan works), deferral
  limits, and a paced disk walk that finds the same as an unpaced one.

### Behaviour changes — read before upgrading
- **Warden now starts in observe-only mode.** `[daemon] dry_run` defaults to
  `true` (it used to be `false` in the code while the docs promised the
  opposite). Detection, events and notifications work as before; actions are
  only reported as "would have done". To remediate: `wardenctl dry-run off`
  (until the next reload or restart) or `dry_run = false` in `warden.toml`.
  An existing `/etc/warden/warden.toml` is never rewritten by an upgrade.
  `install.sh --enforce` sets `dry_run = false` on install; `--dry-run` is
  kept as a no-op alias.
- **The `.deb` no longer enables or starts the service** on install
  (`systemctl enable --now wardend` is yours to run after reviewing the
  config). An upgrade restarts a service that is running and leaves a
  stopped one alone.
- **Name-based protection now needs proof.** `[protection] comm` (and the
  built-in list) protects a process by name only if it is verified to be that
  program: a root-owned, non-writable system binary whose name explains
  `comm`. Protection by `exe`, cgroup/unit and UID is unchanged.
- The unit sets `LimitNOFILE=16384` (fanotify descriptors, `/proc/*/fd`
  scans, control and metrics connections) instead of inheriting the system
  default.

### Security
- **Log injection into `auth.*`.** A login name could contain text that looked
  like a second, "real" source address, so a remote user could make Warden
  block an address of his choice. The `sshd` patterns are anchored on the
  address that `sshd` itself appends last, the per-source tables are bounded,
  and journal lines count only when the kernel-stamped sender is trusted
  (`_UID=0` or a system binary named like the syslog identifier; a missing
  `_EXE` is untrusted — `logger -t sshd` no longer works as a forgery).
- **D-Bus.** Match rules do not stop *directed* signals, so any local user
  could send a `PropertiesChanged` straight to Warden. Signals are accepted
  only from the current owner of `org.freedesktop.systemd1` (tracked through
  `NameOwnerChanged`).
- **Protected by name only when genuine** (see above), so a miner calling
  itself `systemd-udevd` is no longer immune.
- **`memfd` exemption** for container runtimes is decided by the parent's
  trusted system binary, not by a substring of a name the process chose.
- **FIM `trusted_writers`** requires the writer's executable to be a
  root-owned system binary, not just a matching `comm`.
- **Dependencies.** `cargo update` clears the advisories open against
  `rustls-webpki` and `time`; unused features of `ureq` are off (`flate2`,
  `miniz_oxide`, `zlib-rs`, `crc32fast` and friends are gone from the tree).
  CI now runs `cargo audit` and `cargo machete`.

### Fixed
- **Cleanup playbook steps shared one cooldown** — the second `delete_old`
  step of a playbook never ran. The cooldown key is now the full action plus
  its target.
- **A restart repeated the whole cleanup playbook.** Its history is kept in
  `state_dir/disk-cleanups.json` (wall-clock, stale and garbage entries
  dropped on load), so a service restart or reload does not delete again
  what a previous run found useless.
- **"Who is using the disk" came too late** — it now starts at once when a
  disk is critical, not after the cleanup has failed.
- **Control and metrics servers died forever on the first `accept` error**
  (`EMFILE` included). They retry, back off on descriptor exhaustion and cap
  concurrent connections.
- **A slow action stalled the control plane.** `status`, `quarantine`,
  `tuning`, `/health` and shutdown shared a lock with the executor; control
  state now lives outside it (`Handles`), so they answer while a hook runs
  for twenty seconds. The end-to-end suite covers this, including a flood of
  idle connections and SIGTERM during a long hook.
- **A panic in the executor or notifier thread is no longer silent.** Both
  are supervised and restarted, and their queues are bounded. Shutdown gives
  the executor a grace period.
- **Event ids continue from the end of the journal** after a restart,
  independent of the wall clock.
- **`du` memory** depended on the *width* of the tree (a stack of pending
  paths: 200 000 directories measured 80 MiB for one `wardenctl du`, and mail
  spools or caches have millions). The walk is now depth-first over at most 64 open directory
  handles, with caps on aggregated directories (100 000) and remembered
  hard-linked inodes (500 000); nesting deeper than 64 is skipped and the
  report marked partial.
- **`mlockall` defeated `malloc_trim`**: `madvise(DONTNEED)` is refused on
  locked pages, so freed heap was never returned after a big scan. After a
  scan (memory pressure permitting) Warden now does `munlockall` → trim →
  `mlockall` (`warden_sys::selfstat::release_memory`). A fragmented-heap test
  gets 19 MB back where the old code returned nothing.
- **State files are written atomically** (temporary file, `fsync`,
  `rename`): the tuning journal and its persisted state, the FIM store, the
  integrity baseline and the heuristics state, through one helper
  (`warden_sys::util::write_atomic`) instead of separate copies.

### Changed (internal)
- One external-command runner, `warden_sys::cmd::Run`: `poll(2)` plus pidfd
  instead of a `try_wait`/`sleep` loop, bounded output, hard timeout, no hang
  on pipes inherited by a background child. Everything that shells out uses
  it.
- Duplicates removed: three `write_atomic`, two `truncate`, a second
  `malloc_trim`, `mounts::mount_of`, `sustain::end_episode`, `find_suid`

  `md-5` is a workspace dependency.
- CI builds on `master` (it was wired to a branch that does not exist),
  uses `--locked`, and has a dependencies job.

### Added
- [docs/events.md](docs/events.md) — a catalogue of every event: id, severity,

- Tests: spoofed directed D-Bus signals against every bus name; real and
  forged `sshd` lines; flooded source tables; journald sender trust; cleanup

- **A disabled module costs nothing**: no thread, no timer, no buffers, no
  compiled rules. Components are started from the configuration and stop
  themselves when a reload disables them. With everything disabled the daemon
  runs 4 threads instead of 16.

## 0.9.0 

First public release. A host guardian daemon for Linux servers and
workstations, written entirely in Rust — six crates, ~17 500 lines, 142

### Added
- **Memory pressure and swap storms (PSI).** Sustained-stall and thrashing

  connector (no eBPF): privilege escalation, fileless execution, reverse
  shells, crypto-miners, process masquerading, `LD_PRELOAD` injection, ptrace
