# Warden Codegen Audit Kit

**Воспроизводимый аудит машинного кода Rust/LLVM и производительности [Warden](https://github.com/commeta/warden) на Linux x86-64.**

Комплект собирает технические свидетельства по всей цепочке **исходный код → Rust/LLVM → ELF → машинные инструкции → исполнение под нагрузкой**. Он объединяет проверку сборки и тестов, статический анализ ELF, дизассемблирование, LLVM IR/Assembly, моделирование инструкций и измерения работы демона.

> **Назначение.** Инструмент создаёт набор данных для инженерного анализа, поиска узких мест и сравнения изменений. Успешный проход подтверждает выполнение предусмотренных проверок, но не является сертификатом безопасности, доказательством отсутствия дефектов или гарантией производительности в production.

## Возможности

| Направление | Что собирается или проверяется |
| --- | --- |
| Исходники и окружение | Git commit, локальные изменения, `Cargo.lock`, параметры компиляции, ОС, ядро, CPU и toolchain |
| Сборки Rust | Production Release, Release без удаления символов, Release с таблицами строк для сопоставления с исходниками |
| Контроль качества | `cargo fmt`, строгий Clippy, сборка и исполнение тестов workspace, отдельная проверка `mlockall` |
| Машинный код | ELF-заголовки, секции, символы, `objdump`, `llvm-objdump`, распределение размеров кода |
| Компилятор | LLVM IR, Assembly, `cargo-bloat`, `cargo-llvm-lines`; в полном режиме — дополнительные LLVM IR и MIR |
| Статический анализ | Выбранные функции и последовательности инструкций; моделирование прямолинейных блоков через `llvm-mca` |
| Исполнение | CPU, RSS, системные вызовы, штатные сценарии профилирования Warden |
| Нагрузка | Сценарии process/WAF/auth, `perf`-профили при наличии доступа к соответствующим событиям |
| Сохранность свидетельств | Логи этапов, результаты проверок, отчёты JSON, SHA-256 и архив для анализа |

Аудит **не изменяет исходный код Warden**. Для измерений используются отдельные каталоги сборки; диагностическое инструментирование штатных benchmark-скриптов сохраняется отдельно от исходников.

## Требования и безопасность

**Целевая среда:** Ubuntu Server / Xubuntu **24.04**, **x86-64**, предпочтительно отдельная VM с полноценным доступом к интерфейсам ядра Linux.

**Нужно:**

- Python 3.10+, Bash, Git, инструменты сборки C/C++, GNU binutils, LLVM/Clang и `llvm-mca`.
- `rustup` и Rust toolchain **1.99.1** (используется по умолчанию; при необходимости переопределяется).
- Доступ к интернету для получения исходников и установки зависимостей, если отсутствует подготовленный checkout.
- Достаточно свободного места под несколько Release-сборок, отладочные артефакты и архив; полный проход может требовать несколько гигабайт.
- Возможность выполнения отдельных команд через `sudo` для тестов и runtime-сценариев.
- Для полного профилирования — рабочие `/proc`, cgroup и PSI; для аппаратных счётчиков — доступ к PMU со стороны ядра и гипервизора.

**Запускайте аудит обычным пользователем, не через `sudo`.** Скрипт сам вызывает `sudo` для необходимых привилегированных этапов. Установщик зависимостей, напротив, запускается с `sudo`.

> **Внимание:** тесты создают процессы, выполняют файловые операции и генерируют нагрузку. Даже если демон тестируется с `dry_run`, весь комплекс не является безвредным для production-сервера. Используйте изолированную лабораторную VM. Проводящий реальные действия с firewall сценарий не включён в обычный полный проход и требует отдельного явного подтверждения.

Сборщик не отключает системные ограничения `perf` и не меняет политику ядра ради получения аппаратных счётчиков. Если PMU не предоставлен виртуальной машине, это будет отражено в результатах.

## Установка и быстрый запуск

Из каталога распакованного комплекта:

```bash
# Установка пакетов Ubuntu, Rust toolchain и дополнительных утилит
sudo ./install-deps.sh

# Самопроверка комплекта
./tests/check-kit.sh

# Стандартный аудит: сборки, машинный код, lint и Rust-тесты
./run-audit.sh

# Полный аудит: дополнительно runtime-профили, strace и безопасные stress-сценарии
./run-full-audit.sh
```

Оба запуска создают **отдельный каталог результатов** `results/warden-code-audit-<UTC>` и архив рядом с ним. Не используйте один и тот же непустой `--output` повторно.

Если исходники Warden уже находятся на машине:

```bash
./run-audit.sh --repo /home/warden/warden --output /data/warden-audit
```

Для аудита конкретной ревизии из GitHub:

```bash
./run-audit.sh --ref <git-ref-or-commit> --output /data/warden-baseline
```

Полный перечень аргументов:

```bash
./run-audit.sh --help
```

## Режимы работы

### Стандартный проход

```bash
./run-audit.sh
```

Предназначен для регулярной проверки сборок и генерации кода. Включает сбор метаданных, три варианта Release, анализ ELF и LLVM, статические отчёты, форматирование, Clippy и тесты Rust. Нагрузочное профилирование **не выполняется**, если оно не запрошено дополнительными аргументами.

### Полный проход

```bash
./run-full-audit.sh
```

Дополнительно выполняет:

- **21** штатный сценарий `bench/profile.py` (включая `idle`, `process`, `fim`, `waf`, `auth` и `all`).
- Сбор распределения системных вызовов с помощью `strace` для выбранных сценариев.
- **4** нагрузочных сценария без принудительного изменения firewall: `exec_storm`, `waf_v6_unique`, `waf_v6_spread`, `auth_unique`.
- Проверку доступности `perf`; запись аппаратных либо программных данных в зависимости от возможностей среды.
- Дополнительный LLVM IR, MIR и проверки полноты артефактов.

Полный проход требует корректного завершения всех обязательных стадий. Недоступность PMU фиксируется отдельно от успешности программных измерений и не превращает отсутствующие аппаратные данные в «нулевые» счётчики.

### Выборочное runtime-профилирование

```bash
./run-audit.sh --profile --profile-duration 90 --profile-warmup 30
./run-audit.sh --stress --stress-duration 60
./run-audit.sh --profile --profile-scope all
```

По умолчанию `--profile` запускает сценарии `idle`, `process`, `waf`; `--profile-scope all` выбирает все 21 сценарий. Длительность отдельных сценариев может определяться самим upstream benchmark.

### Повторная проверка тестов

```bash
./run-audit.sh --tests-only --repo /path/to/warden --output /data/warden-tests
```

Режим выполняет проверки кода и тесты без повторного построения трёх Release и сбора машинного кода. Не является заменой полного аудита. При необходимости можно увеличить время ожидания подходящих условий для изолированного теста памяти:

```bash
./run-audit.sh --tests-only --repo /path/to/warden \
  --output /data/warden-tests --memory-calm-timeout 300
```

### Дополнительные измерения без повторной сборки

```bash
./continue-audit.sh /path/to/audit-directory --profile --stress --archive
```

Используются уже сохранённые бинарники аудита. Параметры доступных сценариев: `./continue-audit.sh --help`.

### Тесты с воздействием на firewall

Сценарий `block_storm` **не входит** в обычный полный проход. Он затрагивает nftables и должен использоваться **только** на одноразовой VM с известной конфигурацией сети:

```bash
./run-audit.sh --stress-firewall --ack-lab-impact
```

Не запускайте этот режим на сервере с реальными пользовательскими соединениями.

## Воспроизводимость измерений

Для сравнения Warden до и после изменения кода фиксируйте одинаковые условия:

1. **Ревизия и исходники:** Git commit, состояние рабочего дерева, `Cargo.lock` и Cargo features.
2. **Компилятор:** `rustc`, Cargo, профиль Release, `RUSTFLAGS`, LTO и target CPU.
3. **Окружение:** ядро Linux, виртуализация, выделенные vCPU/RAM, доступность PMU.
4. **Нагрузка:** одинаковые сценарии, длительности, наборы входных данных и условия прогрева.
5. **Результат:** сравнивайте CPU, RSS, системные вызовы и корректность обнаружения событий, а не только размер бинарника.

Первую базовую точку рекомендуется снимать без `target-cpu=native`, PGO и нестандартных флагов оптимизации. Альтернативные настройки исследуйте отдельными прогонами.

`--mca-cpu` задаёт модель процессора для `llvm-mca` (по умолчанию `auto`; можно указать конкретную поддерживаемую модель). Эта настройка относится к моделированию инструкций и **сама по себе не меняет архитектуру production-сборки**.

## Результаты аудита

Типовая структура каталога:

```text
results/warden-code-audit-<UTC>/
├── source/                  # checkout Warden при загрузке из GitHub
├── artifacts/
│   ├── wardend.production   # production Release
│   ├── wardend.release-unstripped
│   ├── wardend.symbolized
│   ├── audit-kit/           # снимок использованного инструментария
│   ├── llvm-ir/             # при наличии соответствующего прохода
│   └── mir/                 # полный проход
├── reports/
│   ├── audit-summary.json
│   ├── steps.json
│   ├── run-provenance.json
│   ├── test-validation.json
│   └── codegen/
├── logs/                    # stdout/stderr отдельных этапов
├── runtime-profile/         # результаты профилирования, если запущено
├── runtime-stress/          # результаты нагрузочных сценариев, если запущено
└── SHA256SUMS               # хеши файлов каталога на момент формирования
```

Набор подкаталогов зависит от выбранного режима и доступности инструментов. Полный проход также создаёт файл `*.full-analysis.tar.gz`; стандартный — `*.tar.gz`.

**Файлы, с которых следует начинать анализ:**

| Файл | Назначение |
| --- | --- |
| `reports/audit-summary.json` | Режим, длительность, число шагов, сбои, пропуски, доступность `perf`, полнота полного прохода |
| `reports/steps.json` | Команды, коды завершения, продолжительность, путь к журналу каждой стадии |
| `reports/run-provenance.json` | Ревизия исходников, хеши ELF и `Cargo.lock`, настройки toolchain и состояние `perf` |
| `reports/test-validation.json` | Полнота и результаты проверок Rust-тестов |
| `reports/codegen/` | Анализ ELF, функции, машинные инструкции, результаты `llvm-mca` |
| `reports/profile-all-inventory.json` | Наличие и валидность 21 профиля полного прохода |
| `reports/safe-stress-inventory.json` | Наличие и валидность четырёх стресс-сценариев |
| `logs/` | Первичная диагностика неуспешных команд |

Проверить сводку и список неуспешных шагов:

```bash
jq '{steps_total,steps_failed,steps_skipped,full_pass_complete,bundle_mode,
     perf_hardware_available,perf_record_callgraph_available}' \
  /path/to/audit/reports/audit-summary.json

jq -r '.[] | select(.status != "ok") | [.name,.status,.exit_code,.log] | @tsv' \
  /path/to/audit/reports/steps.json
```

Для полного прохода ищите `full_pass_complete: true`, но также проверяйте инвентари результатов и журналы. Для стандартного прохода `full_pass_complete: null` — ожидаемое значение, а не ошибка.

### Три сборки ELF: важное различие

- **`wardend.production`** — фактический Release по настройкам проекта.
- **`wardend.release-unstripped`** — отдельная Release-сборка с сохранёнными символами.
- **`wardend.symbolized`** — сборка с дополнительной информацией для сопоставления адресов и строк исходного кода.

Это **три разных результата компиляции/линковки**. Совпадение размеров или названий функций не доказывает побайтовую идентичность машинного кода. Сравнение секций `.text` проверяется отдельно; производительность одной сборки нельзя автоматически приписывать другой.

## Как оценивать результаты

**`perf`.** Программные показатели (`task-clock`, переключения контекста, page faults) и выборочные профили могут быть доступны при отсутствии аппаратных событий. Рассчитывайте IPC, CPI, branch-miss rate и cache-miss rate **только** при наличии действительных значений соответствующих аппаратных счётчиков. Права root не компенсируют отсутствие PMU, не экспортируемого гипервизором.

**`llvm-mca`.** Моделирует выбранные **прямолинейные блоки инструкций** для указанной микроархитектуры. Оценки throughput/IPC не учитывают реальную частоту выполнения блоков, распределение переходов, ошибки предсказания, промахи кэша и поведение всей функции. Это инструмент выдвижения гипотез, а не замена профилирования.

**LLVM IR и MIR.** Промежуточные представления полезны для понимания решений компилятора. При `fat LTO` итоговый post-link ELF может существенно отличаться от промежуточных фрагментов кода; заключения об инструкциях следует проверять по финальному бинарнику.

**Счётчики инструкций и размер кода.** Само по себе большое количество ветвлений, `lock`-инструкций, перемещений между регистрами или байтов в функции не доказывает потерю производительности. Сначала определите *hot path* и воспроизведите нагрузку, затем оценивайте стоимость оптимизации с учётом корректности и безопасности.

**Бенчмарки.** CPU и RSS относятся к конкретной конфигурации и сценарию. Сравнивайте повторные прогоны с одинаковыми условиями; для статистически обоснованного ускорения необходимы повторения и контроль разброса измерений.

## Упаковка и передача данных

Создать архив из существующего каталога:

```bash
# Компактная диагностика: отчёты и логи
./pack-results.sh /path/to/audit --diagnostics-only \
  --output /data/warden-diagnostics.tar.gz

# Пакет для технического анализа
./pack-results.sh /path/to/audit \
  --output /data/warden-analysis.tar.gz

# Сырые LLVM/ASM, полное дизассемблирование и perf.data
./pack-results.sh /path/to/audit \
  --include-llvm-raw --include-full-disassembly --include-perf-data \
  --output /data/warden-analysis-raw.tar.gz
```

Имена файлов пакета перечислены в его манифесте. `BUNDLE-SHA256SUMS` подтверждает целостность **включённых в пакет файлов**; `SHA256SUMS` в исходном каталоге относится к его собственному содержимому на момент формирования.

Перед передачей архива проверьте журналы, абсолютные пути, патчи исходников и runtime-артефакты на конфиденциальную информацию. Не запускайте тесты на checkout, содержащем производственные секреты.

## Проверка комплекта

```bash
./tests/check-kit.sh
```

Либо отдельный запуск Python-тестов:

```bash
python3 -m unittest discover -s tests -p 'test_*.py'
```

Самопроверка оценивает интерфейсы CLI, разбор результатов, проверку статусов, инструментирование benchmark-скриптов, модели ELF/`llvm-mca`, архивирование и контрольные суммы. Она **не заменяет** полный запуск на целевой Linux VM. Подробности лабораторной валидации вынесены в [VALIDATION.md](VALIDATION.md).

## Диагностика

| Симптом | Что проверить |
| --- | --- |
| Нет аппаратных счётчиков `perf` | `reports/audit-summary.json`, настройки ядра, доступность PMU в KVM/гипервизоре |
| Не выполнены привилегированные тесты | `sudo`, `logs/cargo_test_*`, `reports/test-validation.json`, cgroup/PSI |
| Ошибка runtime-профиля | `reports/profile-preflight.json`, результаты сценария и сохранённые журналы демона |
| Различаются `.text` разных Release | Отчёт сравнения секций и `reports/run-provenance.json`; не предполагать эквивалентность |
| Ошибка `llvm-mca` | `reports/codegen/llvm-mca/status.json`, модель CPU, исходный блок Assembly |
| Не создан полный архив | `*.bundle.log`, `reports/bundle-full-attempt-failed.txt`, свободное место |
| Недостаточно места на диске | Перенести `--output` на другой том; не использовать `--keep-build` без необходимости |

Для диагностики удобнее сначала открыть журнал конкретного этапа из `reports/steps.json`, а затем связанный JSON-инвентарь: завершение команды с `rc=0` не всегда гарантирует полноту и пригодность полученных метрик.
